What Appeal is, and where the prior conversation left off
Appeal is your CLI library built on one insight: a Python 3 function signature is a complete command-line spec, so the library's only job is to translate between the two domains. Positional params → arguments, keyword-only params → options, annotations → converters, and — the part that makes it special — converters are introspected recursively exactly like command functions, so there's no real distinction between the two. That recursion is what gives you composable pieces for free (the Logging mix-in, options-that-map-options, accumulator[int] via __class_getitem__). Under the hood it compiles each signature tree to a little "Charm" bytecode program and runs it against the command-line with a two-phase interpreter.

Two thoughts on the consequences:
Curly-brace literals in user docstrings need escaping somewhere. If {argument} is the placeholder syntax, then a user's Arguments: description that contains a literal { (JSON examples, format strings, dict literals in code blocks) will collide. There are three workable answers and they're all fine, but the choice should be deliberate:

Double them ({{ for literal {). Standard Python format-string convention, immediately recognized — but adds an escaping tax to every docstring that mentions JSON or dicts.
Restrict placeholder recognition to the template-parsing pass only. The user's description text is treated as opaque — {argument} inside the documentation body never substitutes, because substitution happens only when parsing the structural template. Substitution and content live in different processing phases, so they can't conflict.
Code lines bypass placeholder syntax. Inside the four-space-indented code-line regions, braces are literal. The convention already exists in your design (code lines suppress word wrap); extending "and they suppress placeholder substitution" is a small, intuitive extension.

Option 2 is the cleanest because it doesn't ask the user to remember anything — placeholders are a template-author concept, not a docstring-author concept. The template author writing {argument} in the layout template lives in a different world than the command author writing prose. They're never editing the same file. Different phases, different rules, no escaping needed in the common case.
"Always in pairs, {argument} first, initially two pairs" is the right starting constraint. Strict structural requirements make the parser trivial and the error messages obvious. The "initially" hints at future relaxation — single-pair templates ("here's one item, repeat forever") or three-pair templates (declaring the repetition explicitly with the third). I'd resist relaxing it. Two-pair is the structurally minimum form that lets you see the separator between items in the template itself, which is the whole reason this approach beats concatenation. One-pair templates would force you to invent a separate "what goes between items" syntax, and you're back where you started.
The strict-pair rule also gives you a clean error message: "the Arguments template must contain exactly two {argument} and two {documentation} placeholders, alternating, with {argument} first." That's diagnosable on read. No clever parser.

The literal-substring approach means the placeholder names are only meaningful at template-parsing time, never inside the description body. A user writing {verbose} or {some JSON example} in their docstring is just text. No escaping, no special-casing of code lines, no phase-distinction the user has to learn. The brace-literal problem evaporates entirely.
It also makes the template parser laughably simple — partition twice to find {argument} and {documentation}, validate they're on lines by themselves, walk through finding the second pair the same way, and the strings before/between/after the four placeholders are your literal layout segments. No escape sequences to handle, no recursive descent, no AST. Forty lines of code, maybe.
And the strictness of "exactly two pairs, on lines by themselves, {argument} first" pays off here especially: each constraint corresponds directly to a partition-and-check step, and any violation has an obvious error message at the point of violation. "Expected {argument} on a line by itself; found it followed by other text on line 7." That's the kind of error message you can write without thinking.
